### 存檔裡的 `src_ok` 顯示 159/176，那不是失敗

存檔 JSON 是舊計分邏輯產出的。少的 17 題**全部**是 `mni: true`（must_not_infer）——它們的正解就是「不要引用任何東西」，而且都 `grounded: false` / `ok: true` 正確拒答了。舊計分仍給這類題目填 `expected_source_id`，於是把 17 次正確的拒答算成引用失敗。

分母只含可回答的題目時，引用正確率是 **159/159**。對外要報的是這個數字。

`run_eval.py` 已於 2026-08-14 修正：mni 題的 `src_ok` 記為 `null`、新增 `src_scored: false`，並直接輸出 hit@1。下次重跑後這一小節就可以刪掉。

## 歷史輪次

只保留最新一輪。先前的輪次（7/18 → 23/52 → 25/52 → 45/52 → 52/52）原始檔仍在 `C:\Protech\admin-replay\kb\`，未納入版控。

最後一次躍升（45/52 → 52/52）分兩步，成因都是前一輪 `###` 切分的副作用：

- **45 → 51**：檢索命中的是子段，而截圖只在母段，6 題因此 `images=[]`。`export_kb.py` 把入口截圖帶進每個工程對應子段後修復。
- **51 → 52**：切分後母段只剩 Symbol Index —— 一堆符號、零個端點，但它的說明文字寫著「原始碼符號、API、ViewModel」，對「X 會打哪支 API」是最強的 BM25 誘餌。retrieval probe 實測「供應時段會打哪支 API?」的 top-8 只撈到母段，帶 `GET /v1/business/periods` 的子段沒進榜，模型如實回答「有符號但沒有端點」。母段補上 **Endpoint Index**（該模組所有 verified 端點的去重聯集）後修復。

第二點是通則不是特例：模組名出現在每個畫面段的標題裡，module-name-heavy 的查詢會被畫面段吃掉（該題 BM25 排 10，靠向量排 1 才擠進 fused 3）。與其把子段推進 top-8，不如讓穩定命中的母段自己帶答案。
